# Подготовка release PR

Использовать при запросе подготовки релиза. Все пути ниже — от корня репозитория. Соблюдать `AGENTS.md`; процесс и восстановление после ошибок описаны в `docs/agent-setup.md`, раздел «PR и релизы».

1. Найти открытый release PR от release-please в `main` (ссылка/номер из запроса либо список PR репозитория). Проверить его автора, базовую ветку, служебное тело и изменения версии. Если подходящих PR несколько — уточнить выбор; если нет — сообщить состояние workflow Release. Не создавать вместо него локальный релиз или тег.
2. Проверить рабочее дерево и перейти в ветку выбранного PR, сохранив чужие изменения. Версию брать из этого PR: `version.txt`, `.release-please-manifest.json` (ключ `.`) и `versionMajor/Minor/Patch` в `app/build.gradle.kts` должны совпадать. Если пользователь указал версию, сверить её с PR; расхождение не исправлять произвольным bump. Сохранить маркеры `x-release-please-*`. Для текущей формулы `versionCode` minor и patch должны быть меньше 100.
3. Определить предыдущий опубликованный стабильный GitHub Release и его тег; изучить полные тела всех коммитов `git log <prev-tag>..HEAD --format="=== %h %s ===%n%b%n" --reverse` и итоговый diff. Не брать неопубликованный draft за предыдущий релиз. Проверить, что целевой тег `v<версия>` ещё не существует; существующие теги не перезаписывать.
4. Сформировать `RELEASE_NOTES.md` с заголовком `# v<версия>`:
   - Группировать по пользовательским фичам, а не коммитам.
   - Фичи и заметные улучшения описывать кратко, без деталей реализации.
   - Фиксы багов предыдущих версий давать одной строкой. Не включать баги, появившиеся и исправленные внутри текущего релиза.
   - Внутренние изменения объединять в одну строку; категории использовать, когда они помогают чтению.
   - Каждое утверждение сверять с итоговым кодом. При первом релизе после миграции проверить также старые non-conventional коммиты: в автоматическом черновике их может не быть.
   - Служебную структуру тела release PR, его заголовок и метки сохранять: release-please читает их при выпуске. Итоговые русские notes хранятся в файле.
5. До скриншотов и проверок выполнить `node scripts/updateBundledSvp.mjs`: он скачивает `sbg-vanilla-plus.user.js` из последнего стабильного GitHub Release SVP, проверяет метаданные, размер и SHA-256 (если он доступен в API), затем атомарно обновляет `app/src/main/assets/scripts/sbg-vanilla-plus.user.js`. При ошибке сети/проверки не использовать старый бандл как готовый релиз. Зафиксировать версию SVP из вывода; включить изменённый `.user.js` в тот же release PR. Затем после проверки обновлённой версии прочитать `.agents/skills/scout-screenshots/SKILL.md`, выполнить генерацию и визуальную проверку трёх README-скриншотов. Затем прочитать `.agents/skills/scout-visual-regression/SKILL.md`, обновить baseline и проверить повторным сравнением: номер версии и версия SVP видны в UI.
6. Прочитать `.agents/skills/scout-verify/SKILL.md` и выполнить полный набор проверок. Выполнить `node scripts/checkRelease.mjs`, `node --test scripts/checkRelease.test.mjs scripts/updateBundledSvp.test.mjs` и `node scripts/updateBundledSvp.mjs --check`. Последняя команда сверяет весь файл с актуальным release-артефактом без записи. Если вышел новый SVP, повторить обновление, проверки, README-скриншоты и visual regression baseline до коммита. Сверить версию собранного APK (штатным `apkanalyzer manifest version-name/version-code`), заголовок notes и ожидаемый тег. Если проверки или скриншоты недоступны, сообщить точную причину и оставить подготовленные файлы; не коммитить непроверенный результат как готовый релиз.
7. Проверить diff. Закоммитить подготовленные notes, PNG и обновлённый бандл SVP в ветку release PR с conventional-заголовком (например, `chore: подготовить материалы релиза 1.3.0`), добавляя только относящиеся к релизу файлы явными путями. Версия уже изменена ботом в этой ветке; `version.txt`, manifest, Gradle, notes, три README-PNG, изменённые visual regression baseline и бандл SVP должны войти в один итоговый squash-коммит PR.
8. Сообщить PR, версию, локальный коммит и результаты проверок. Перед будущим merge проверить актуальный HEAD: если release-please обновил PR, даже без изменения версии, повторно сверить весь диапазон, версию, notes, PNG, актуальность SVP (`node scripts/updateBundledSvp.mjs --check`) и проверки. Непосредственно перед merge повторить проверку актуальности SVP, даже если HEAD не менялся. При ожидающем CI проверить необходимость `Approve workflows to run`.

По умолчанию не пушить; push подготовленной ветки выполнять только если он входит в запрос пользователя. Не создавать локальный тег, не выполнять merge и не публиковать релиз в рамках подготовки. Ручной squash-merge release PR запускает workflow, который создаёт тег и draft, проверяет актуальность бандла SVP до сборки и непосредственно перед публикацией, собирает и проверяет подписанный APK и публикует его с `RELEASE_NOTES.md`. Если SVP обновился уже после merge, не переписывать тег и не менять файлы только на CI runner: подготовить следующий release PR со свежим бандлом; устаревший draft не публиковать.
