# Правила работы над проектом

SBG Scout — Android-клиент для SBG (мобильная браузерная геолокационная игра). WebView с менеджером юзерскриптов, кешированием ассетов, проверкой обновлений.

Общие инструкции для Codex и Claude Code. Редактировать этот файл; `CLAUDE.md` только импортирует его.

## Окружение и скиллы

- Подготовка окружения, команды для PowerShell и Bash: [docs/agent-setup.md](docs/agent-setup.md).
- В Windows окружение устанавливает `scripts/setupAndroid.ps1`; общие команды человека и агентов — `scripts/android.ps1` (`doctor`, `build`, `run`, `test`, `verify`, `logs`, `stop`). Для автоматической проверки debug-запуска использовать `run -Offline`, для UI-flow — `test` с `FakeGameServer`. Запуск PowerShell и доступ из Codex/Claude описаны в `docs/agent-setup.md`.
- Исходники приложения: `app/src/main/`; JVM-тесты: `app/src/test/`; e2e: `app/src/androidTest/`; тестовая конфигурация: `app/src/instr/`.
- Общий источник скиллов — `.agents/skills/scout-*/SKILL.md`. Codex обнаруживает их напрямую; `.claude/skills/` содержит генерируемые копии для Claude Code. Менять только исходники, затем запускать `node scripts/syncAgentSkills.mjs`. Копии коммитятся вместе с исходниками; CI проверяет их актуальность через `node scripts/syncAgentSkills.mjs --check`.
- При проверке приложения использовать `scout-verify`; для README-скриншотов — `scout-screenshots`; для visual regression — `scout-visual-regression`; для подготовки release PR от release-please — `scout-release`; для текста анонса — `scout-announce`. В Codex: `$scout-release`, в Claude: `/scout-release`.
- Скилл можно прочитать по пути вручную, если текущая сессия ещё не обновила список. Новые скиллы называть с префиксом `scout-`.

## Критические запреты (нарушение = перманентный бан в игре)

1. **Запрещена подмена GPS**
2. **Запрещена автоматизация** игровых действий
3. **Запрещён мультиаккаунт**
4. **Запрещена модификация запросов** к серверу

## Проверки перед коммитом и push

Выбирать проверки по **всему diff задачи**, а не запускать Android CI после любых правок:

`node scripts/planChecks.mjs --base origin/main`

План включает коммиты ветки, staged/unstaged и новые неигнорируемые файлы. Выполнить команды из `commands`; в PowerShell заменить `./gradlew` на `./gradlew.bat`. Области проверок и исключения описаны в [docs/ci-checks.md](docs/ci-checks.md). Обычная документация не требует SDK, Android-сборок или эмулятора; `RELEASE_NOTES.md` проверяется как релизный файл. При изменении исходников скиллов сначала выполнить `node scripts/syncAgentSkills.mjs` и коммитить копии вместе с исходниками.

Для явной полной проверки использовать `node scripts/planChecks.mjs --full`; при подготовке release PR — `--release-pr` (полный набор и актуальность SVP). Ошибка определения diff не означает, что проверок нет: исправить причину или выполнить полный набор. Неизвестные файлы включают полный набор без сетевой проверки SVP.

Android-набор: `./gradlew ktlintCheck detekt lintInstr testInstrUnitTest assembleDebug assembleInstr assembleRelease`. `testInstrUnitTest` — обычные JVM-тесты из `app/src/test/`, без эмулятора: из-за `testBuildType = "instr"` задачи `testDebugUnitTest` нет. Инструментальные тесты запускаются через `connectedInstrAndroidTest`; `--tests` применим только к JVM-тестам.

Если план включает e2e или правка затрагивает поведение, покрываемое e2e, выполнить локальную проверку ДО push. Для изменения отдельного теста/flow минимум — соответствующий класс через `connectedInstrAndroidTest "-Pandroid.testInstrumentationRunnerArguments.class=полное.ИмяКласса"`; для общих POM, E2ETestBase и инфраструктуры прогнать полный затронутый набор. Полный набор в Windows запускать через `scripts/android.ps1 test -AllTests` (шарды на свежем эмуляторе), а не одной командой Gradle: эмулятор не освобождает около 400 МБ на тест и исчерпывает память. Эмулятор: API 33, Pixel 4, WebView 101, образ `default` без Google Play; тесты только через FakeGameServer. Visual regression проверять отдельно, если она выбрана планом. Параллельным worktree нужны отдельные AVD/порты: не переустанавливать test APK на эмуляторе другой задачи; подробности и обход длинных путей Windows — в docs/agent-setup.md.

Если проверка падает — исправить причину и повторить затронутые проверки. Если JDK, SDK, зависимости или эмулятор недоступны, указать точную причину и непройденные проверки; не выдавать их за успешные. Инструкции подготовки окружения хранить в репозитории.

## Исследование

- Перед новой фичей/правкой игрового поведения, WebView или юзерскриптов — **сначала искать в `refs/`** (`rg`, чтение файлов). Если `refs/` нет — запустить `node scripts/fetchRefs.mjs`. Для правок только документации/инструментов агентов загрузка игровых референсов не нужна.
- При проблемах с WebView, API игры или платформой — **сначала проверить refs/anmiles/** (референсный APK), потом документация
- Исходники SVP можно также искать в соседней директории (`../sbg-vanilla-plus`) — это рабочая директория разработки SVP. Может содержать незакоммиченные изменения: проверять актуальность по `git log` и `git status`. Папку `dist/` там не смотреть — собирается редко, скорее всего неактуальна. В целом лучше использовать `refs/svp/`, но иногда соседняя директория может быть полезна

## Вшитые скрипты

- Перед каждым релизом проверять `node scripts/updateBundledSvp.mjs --check`. Если бандл устарел, выполнить обновление без `--check` в отдельном PR и влить его до подготовки release PR. Prepare release только проверяет бандл. Перед merge снова выполнить `--check`. CI release PR и публикация блокируют устаревший или изменённый бандл. Обычные сборки не требуют сети для обновления SVP.
- **Вшитые скрипты (`app/src/main/assets/scripts/`) обновляются ТОЛЬКО из GitHub releases.** Соседние директории (`../sbg-vanilla-plus` и т.д.) — для исследования исходников, НЕ для вшивания в APK. Источник для вшивания — всегда release-артефакт с GitHub.

## Код

- **Не смешивать Material3 и MaterialComponents.** Приложение использует `Theme.MaterialComponents` — все стили виджетов должны быть из `Widget.MaterialComponents.*`. Стили `Widget.Material3.*` дают некорректные цвета в MaterialComponents-теме. Перед применением стиля — проверить совместимость с темой приложения.
- Любое написание или изменение кода должно соответствовать docs/dev-principles.md и docs/codestyle.md
- Любое изменение в архитектуре или в ключевых механизмах должно соответствовать docs/architecture.md. **Обновлять docs/architecture.md сразу при изменении архитектуры — не спрашивать.**
- **Не угадывать** URL, DOM-классы/ID, структуру страниц и любые факты об игре — искать в refs/ (в т.ч. refs/anmiles/) или спросить пользователя

## Тесты

- **Новое UI-поведение требует e2e-теста.** Unit-тест на изолированную логику (GameUrls, утилиты) не заменяет e2e-тест на UI-flow: диалоги, счётчики тапов, навигация, сохранение состояния в prefs. E2e-тесты живут в `app/src/androidTest/`, запускаются через `connectedInstrAndroidTest`.
- Правило: любое новое поведение покрывается ЛИБО unit-тестом (если логика изолируема), ЛИБО e2e-тестом (если поведение завязано на UI или Activity), ЛИБО обоими.

- **Перед UI-правкой проверить полноту visual regression покрытия.** Перечислить изменяемые визуальные состояния и переходы между ними, включая тему, локаль, флаги и фазы загрузки или анимации; сопоставить каждое состояние со сценарием в `app/src/androidTest/.../e2e/visualregression/` и PNG в `.github/images/visual-regression/`. Если изменяемое состояние не покрыто, добавить сценарий и baseline в том же коммите. Для изменённых существующих сценариев запустить `./gradlew :app:updateVisualRegressionBaselines` (скилл `scout-visual-regression`) и закоммитить обновлённые PNG вместе с кодом. Один неподвижный кадр не проверяет анимацию: её переходы требуют отдельного e2e-утверждения. Перед коммитом открыть actual и baseline в исходном разрешении и проверить, что видны нужное состояние и штатные элементы интерфейса. Подробности архитектуры VR - в `docs/architecture.md`.

## Скриншоты README

- Каждый новый самостоятельный экран SBG Scout, который пользователь видит при обычном использовании, включая экран загрузки, добавить в раздел «Скриншоты» `README.md` в том же коммите, что и экран. До правки найти все места, где перечислены README-снимки. Добавить e2e-генератор с `@ReadmeScreenshot`, имя в `readmeScreenshotNames` (`app/build.gradle.kts`), PNG из генератора, `<img>` с осмысленным `alt` в `README.md` и файл в список `.github/workflows/prepare-release.yml`; обновить проверку этого списка и скилл `scout-screenshots`. Не откладывать снимок до релиза. Если неясно, является ли новый UI отдельным экраном, согласовать это с пользователем до исключения из README.
- Скриншоты в `.github/images/screenshots/` (`game_loading.png`, `game_settings.png`, `settings.png`, `script-manager.png`) обновляются как часть каждого релиза тем же коммитом, что bump версии в `app/build.gradle.kts`.
- Источник истины — e2e-генератор, не ручные снимки. Скилл `scout-screenshots` запускает тест-классы в `app/src/androidTest/.../e2e/screenshots/` через `:app:updateReadmeScreenshots` (gradle-обёртка над `connectedInstrAndroidTest` с фильтром по `@ReadmeScreenshot` + `copyReadmeScreenshots`). Эмулятор: API 33, Pixel 4, WebView 101. Локаль приложения форсится на русскую внутри тестов через `LocaleManager.setApplicationLocales`, локаль эмулятора не имеет значения.
- При добавлении или изменении README-снимка проверить, что его e2e-сценарий запускается в функциональном CI, а сохранённый PNG соответствует реальному рендеру приложения в исходном разрешении. Искусственно вызванное состояние допустимо; вид штатных элементов, включая индикаторы и текст, должен остаться настоящим. Если в кадре есть анимация, отдельно проверить её движение e2e-тестом и форму видимого кадра. README PNG пересоздаются локально; CI не сравнивает их с файлами в репозитории.
- В `scout-release` скриншоты обновляются ПОСЛЕ `versionMajor`/`versionMinor`/`versionPatch` в `app/build.gradle.kts`, чтобы новая версия попала на экран настроек из `BuildConfig.VERSION_NAME`.
- Итоговый squash-коммит release PR включает `RELEASE_NOTES.md`, `version.txt`, `.release-please-manifest.json`, `app/build.gradle.kts` и `.github/images/screenshots/` одной транзакцией; актуальный бандл SVP уже влит отдельным PR. Скилл скриншотов сам не коммитит — это решает вызывающий сценарий.
- `game_loading.png` снимает экран загрузки игры на фикстуре `app-page-loading-screen-realistic.html`: разметка и тексты этапов из `refs/game/index.html` без стилей игры.
- `game_settings.png` использует mock-фикстуру (`app-page-with-settings-content-realistic.html`), потому что полные стили игры не лежат в репо. Локальный snapshot в `refs/game/private/` (gitignored через `/refs/`) подхватывается задачей `inlineGameSnapshot` как override фикстуры.

## Референсы

Загрузка: `node scripts/fetchRefs.mjs` → `refs/`

| Референс | Путь в refs/ | Назначение |
|---|---|---|
| SVP sources | `svp/src/` | Исходники SVP |
| SVP release | `releases/sbg-vanilla-plus.user.js` | Собранный SVP .user.js |
| Anmiles APK | `anmiles/` | WebView-настройки, авторизация, JS-мосты, инжекция |
| EUI sources | `eui/src/` | Исходники EUI для понимания API |
| CUI sources | `cui/` | Исходники CUI |
| EUI/CUI releases | `releases/` | Собранные .user.js |
| OpenLayers | `ol/ol.js` | Картографическая библиотека игры |
| Login page HTML | `game/login.html` | Страница авторизации (`sbg-game.ru/login`); редирект с `/app` для неавторизованных |
| Game HTML + script | `game/index.html`, `game/script.js` | Страница игры (`sbg-game.ru/app`); стартовый URL приложения |

Ручной контент (не скачивается автоматически; см. инструкции в stub-файлах):
- `refs/game/dom/login-body.html` — DOM экрана авторизации (из DevTools)
- `refs/game/dom/game-body.html` — DOM игрового экрана после авторизации (из DevTools)
- `refs/game/css/variables.css` — CSS custom properties (из DevTools)
- `refs/game/har/` — HAR-файлы сетевых запросов из DevTools (авторизация, загрузка игры)
- `refs/screenshots/` — скриншоты UI

## PR и релизы

- Заголовки PR — Conventional Commits; merge в main — только squash с заголовком PR. Правила версий и настройки GitHub: [docs/agent-setup.md](docs/agent-setup.md#pr-и-релизы).
- **Соавторство в PR.** При создании и обновлении PR собирай `Co-authored-by` из всех его коммитов в завершающий абзац описания, сохраняя уже указанных соавторов и служебный текст бота. Удаляй дубли по паре имя/email; разные имена с одним email не объединяй. Перед передачей на merge сверяй с текущими коммитами.
- После внесения изменений в PR обновлять его описание, чтобы оно отражало итоговые изменения и фактические результаты проверок, включая ограничения и непройденные проверки. Перед завершением работы сверять описание с текущим diff; в PR ботов сохранять служебную структуру описания.
- Не оставлять незакоммиченные изменения по завершении работы: любые внесённые правки должны быть закоммичены, запушены и находиться либо в `main`, либо в открытом PR.
- После закрытия или вливания PR удалять его remote-ветку. Перед удалением проверять состояние PR и имя его head-ветки; `main` и другие защищённые ветки не удалять.
- Версию предлагает release-please в отдельном PR. Готовить notes и скриншоты в его ветке; не создавать локальный тег. Выпуск происходит после ручного merge подготовленного release PR.
- В release PR сохранять служебную структуру тела, заголовок и метки бота. После его обновлений повторно проверять версию, notes и PNG перед merge.

## Release notes

- При запросе о релизе или дополнении notes сначала прочитать [процесс релиза](docs/releasing.md) и выполнить `node scripts/releaseNotes.mjs inspect`. Черновик хранится в комментарии существующего release PR; после редактуры пользователя финальные notes помещаются в описание PR. Изменения процесса и скиллов сначала вливаются отдельным PR.
- **Делить notes на «Возможности» и «Исправления».** Новое поведение, улучшения и обновления идут в первый раздел; баги предыдущих версий — во второй. Пустые разделы не выводить. Смешанные пункты разделять по пользовательским эффектам, группировать похожие PR внутри раздела.
- **Похожие PR объединять; писать очень коротко.** Один пункт на пользовательскую фичу или общую область изменений, одна короткая фраза со ссылками на все относящиеся PR. Сохранять существенные условия исправлений. Проверить каждый PR полного диапазона: включить в группу либо обосновать исключение; краткость не заменяет полноту проверки.
- **Исключать технические правки без подтверждённого пользовательского эффекта.** CI, агентские инструменты, рефакторинг и обслуживание зависимостей сами по себе не являются пользовательским изменением. Каждый исключённый PR учесть с обоснованием в сверке диапазона.
- **Обновление Vanilla+ — один пункт.** При изменении бандла с прошлого опубликованного стабильного релиза писать ровно «Обновлён вшитый скрипт Vanilla+.» и перечислять все PR, обновлявшие бандл. При одинаковом итоговом бандле пункт не нужен. Автоматика собирает этот пункт в черновике; финальное описание согласуется с пользователем по `docs/releasing.md`.
- **Не включать внутренние фиксы текущего релиза.** Если баг появился и был исправлен в рамках одного релиза — пользователь предыдущей версии его не видел, упоминать нечего. В release notes попадают только фиксы багов предыдущих версий.
- **Верифицировать каждое утверждение по коду.** Коммит-сообщения могут быть неточными или описывать промежуточное состояние. Перед включением в release notes — проверить в коде, что фича реально делает. Нарушение = враньё в changelog.
