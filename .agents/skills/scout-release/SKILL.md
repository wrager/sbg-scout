Прочитать AGENTS.md и [общий процесс релиза](../../../docs/releasing.md).
Механика подготовки и публикации определяется этим документом и командами проекта.

Подготовка не разрешает merge, тег или публикацию.
Перед публикацией или изменением комментария, правкой PR, запуском Prepare release
и merge показать конкретное действие и полный готовый текст, если он есть,
затем получить отдельное явное подтверждение пользователя.
Подтверждение плана не заменяет подтверждение внешнего действия.
Не создавать локальные теги; опубликованные теги и assets не переписывать.

## Начало работы

Проверить рабочее дерево и актуальные инструкции в main: открытая локальная ветка
может содержать прежний процесс выпуска. Получить ветку существующего release PR,
создать локальную ветку без tracking и выполнить `node scripts/releaseNotes.mjs inspect`.
Сохранить найденные номер PR, head, base и ссылку на помеченный комментарий.
Не подменять отсутствующий release PR ручным bump версии.

Если пользователь просит полный цикл, агент выполняет и действия в GitHub,
получая подтверждения в указанных выше точках. Не поручать пользователю команды,
доступные агенту. При отсутствии доступа к физическому телефону отдельно согласовать
проверку обновления на эмуляторе; она не доказывает поведение конкретного телефона.

## Подготовка текста

До предложения готовых notes прочитать полные сообщения коммитов от предыдущего
опубликованного стабильного тега до head, итоговый код и обсуждения относящихся PR.
Сверить каждый PR полного диапазона с группой notes либо обоснованным исключением
по правилам `docs/releasing.md`. Похожие PR объединять в один пункт: одна очень
короткая фраза со ссылками на все PR группы и существенными условиями исправлений.
Разделять notes на «Возможности» и «Исправления» по `docs/releasing.md`: пустые
разделы не выводить, смешанные пункты разделять по пользовательским эффектам.
Технические правки без подтверждённого пользовательского эффекта исключать,
записывая обоснование для каждого PR в сверке диапазона.
Сохранять ранее согласованные подтверждения в комментарии.
Не выдавать версии библиотек или заголовки коммитов за доказательство исправленного бага.

Комментарий используется для предварительных формулировок и подтверждений.
Показать проект финальных notes и дать пользователю отредактировать его.
После редактуры проверить формулировки, показать полное готовое описание PR
с финальным блоком notes и подписью и запросить подтверждение его публикации.
Сохранить служебную структуру бота по `docs/releasing.md`.
Не редактировать сгенерированные `RELEASE_NOTES.md` и `.release-notes.json` вручную.

После обновления PR ботом проверить финальный блок и материалы заново.
Если бот перезаписал текст, восстановить и согласовать его, повторить подготовку.
Не добавлять отдельную блокировку Release Please.

## Изменение процесса во время выпуска

Если поручено развивать этот скилл, добавлять проверенные решения по ходу работы,
не превращая его в журнал конкретного релиза или копию общего алгоритма.
Менять только `.agents/skills/scout-release/`, затем запускать
`node scripts/syncAgentSkills.mjs` и читать diff сгенерированной копии Claude.
Проверять синхронизацию и изменённый скилл до коммита.

Изменения процесса и скиллов выносить в отдельный PR и дождаться его вливания
в main до подготовки релиза. После этого получить актуальный release PR
и продолжить по обновлённым инструкциям. Отпечаток подготовки охватывает всё
дерево, включая скиллы: последующая правка требует повторной подготовки.

## После merge

Проверить завершение публикации, точное совпадение заголовка и notes, наличие
и скачивание подписанного APK. Сам merge не доказывает, что релиз опубликован.
При ошибке прочитать [восстановление публикации](../../../docs/releasing.md#восстановление-публикации):
rerun исполняет исходный workflow, поэтому исправление CI требует отдельного PR.
Перед ручным запуском восстановления показать main SHA, исходный SHA тега,
состояние draft и assets, точные согласованные notes; получить отдельное
подтверждение запуска, включающего публикацию в CI. Оба пути используют GitHub App
по `docs/agent-setup.md`; до запуска проверить наличие переменной и секрета.
Не заменять pipeline ручной загрузкой APK через CLI. Ключ и токен не передавать
в inputs workflow или чат. Существующие теги и assets не переписывать.
